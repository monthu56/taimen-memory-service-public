# ADR-002: Защита персональных данных — допуски токенов, маскирование, журнал (152-ФЗ)

## Status

Accepted (2026-07-06, объём согласован с владельцем: два уровня токенов;
авто-детекция + явная метка; журнал чтения ПДн; демо-токен интегратора — маскированный).

## Context

Память хранит статьи/факты, куда попадают персональные данные (телефоны, email,
паспорт, СНИЛС…). Сервис открыт внешним интеграторам по Bearer-токену; заказчики
требуют обработку ПДн в контуре РФ (152-ФЗ). До сих пор любой валидный токен видел
весь контент; механизма учёта и ограничения доступа к ПДн не было.

## Decision

1. **Feature-flag `CB_PII_PROTECTION` (default: off).** Выключен — поведение
   сервиса байт-в-байт прежнее (инвариант обратной совместимости контракта).
2. **Два уровня допуска токенов**: `CB_SERVER_API_KEYS_PII` (список через запятую)
   — полный допуск; базовый `CB_SERVER_API_KEY` при включённой защите — маскированная
   выдача. Реализация — `authenticate() -> Principal` поверх прежнего `require_auth`
   (сигнатуры маршрутов не ломаются), сравнение токенов — constant-time.
3. **Двойной барьер**:
   - *запись*: `retain` авто-детектирует ПДн регексами (`core/pii.py`) и принимает
     явную метку (`pii`, `pii_categories`) — узел маркируется в properties
     (учёт/инвентаризация ПДн);
   - *чтение*: для masked-токена все текстовые поля выдачи (query/recall/search/node)
     маскируются `[ПДн:<категория>]` **по паттернам, независимо от маркировки** —
     пропущенное при записи не утекает; ответ помечается `pii_masked: true`.
4. **Журнал доступа**: выдача немаскированных ПДн full-токену пишет `audit_event`
   `action="pii_access"` (маршрут, категории, метка токена — не сам токен) в тот же
   аудит-контур, что и delete (ADR-001); читается через `GET /api/brain/trace/{id}`.
   Ошибка журнала не роняет выдачу.
5. **Детектор**: телефон РФ, email, паспорт РФ, СНИЛС, карта (+Лун), ИНН — только
   с текстовым маркером «ИНН». **ФИО и даты рождения регексами не детектируются**
   (неприемлемый шум) — покрываются явной меткой при записи.

## Соответствие механизмов 152-ФЗ

| Требование | Механизм |
|---|---|
| Локализация ПДн в РФ | развёртывание на сервере РФ (инфраструктурно) |
| Ограничение доступа (допуски) | уровни токенов + маскирование выдачи |
| Учёт операций с ПДн | журнал `pii_access` + аудит retain/delete, трейс по `trace_id` |
| Уничтожение по требованию субъекта | `DELETE /api/brain/nodes/{key}` с аудитом (ADR-001) |
| Маркировка/инвентаризация ПДн | авто-детекция + `pii`/`pii_categories` на узлах |

## Consequences

- Контракт аддитивен: новые поля (`pii_masked`, `pii_categories`), новые env; при
  выключенном флаге — ноль изменений.
- Маскированная выдача может ломать точность LLM-ответов потребителя на ПДн-вопросах
  — это осознанно: без допуска ПДн не выдаются.
- Журнал `pii_access` растит граф на каждое чтение ПДн full-токеном; на демо это
  приемлемо, для прод-нагрузки предусмотреть агрегацию/ротацию (отдельное решение).
- Регекс-детектор имеет ложноотрицательные (ФИО, адреса, нестандартные форматы) —
  зона ответственности интегратора: явная метка при импорте ПДн-контента.

## Alternatives

- **LLM-классификатор ПДн** — отклонено для MVP: латентность и стоимость на каждом
  чтении/записи, зависимость от внешнего LLM в контуре ПДн. Возможное расширение.
- **Допуски по категориям ПДн** — отклонено: двух уровней достаточно для текущих
  потребителей; модель Principal расширяема без слома контракта.
- **Шифрование ПДн-полей в БД** — отклонено на этом шаге: защищает от другого
  класса угроз (доступ к диску/дампу), не от избыточной выдачи по API; БД и так в
  контролируемом контуре. Кандидат в следующие шаги.
