# ADR-010: Задержки графа лечим JIT/пулом/LLM, а не переписыванием на Rust

## Status

Accepted (2026-09-12; реализовано — `CB_DB_JIT=false` в `core/config.py`,
`tests/test_db_session_options.py`; переписывание на Rust не начато). Подготовлено
2026-07-27 по запросу владельца «переписать сервис на Rust, чтобы максимально
оптимизировать задержки графа».

## Context

Поставлен вопрос о переписывании сервиса на Rust ради задержек графа. Прежде чем
принимать решение такого масштаба, задержки были **измерены** на живом инстансе
(`memory-demo` на стенде: граф `memory_demo`, namespace `sea-demo`).

### Что показали замеры

**Граф крошечный, а запросы медленные** — значит дело не в объёме данных:
1037 вершин, 758 рёбер, 134 чанка в векторном индексе.

`EXPLAIN (ANALYZE, BUFFERS)` на `expand_neighbors(hops=1)`:

```
Execution Time: 577.590 ms
  JIT: Functions: 80
       Generation 6.187 ms, Inlining 110.916 ms,
       Optimization 198.369 ms, Emission 167.644 ms, Total 483.116 ms
  Полезная работа плана: HashAggregate actual time=39.572..39.584
  Nested Loop: estimated rows=1694508711, actual rows=1
```

**84 % времени графового запроса — это LLVM-компиляция плана, а не обход графа.**
Причина: AGE отдаёт планировщику мусорную оценку кардинальности (1.69 млрд строк
при 1037 вершинах), стоимость плана выходит 131 427 517 при `jit_above_cost=100000`
и `jit_inline_above_cost`/`jit_optimize_above_cost=500000` — включаются самые дорогие
стадии JIT. А поскольку соединение открывается и закрывается на каждый HTTP-запрос
(`core/db.py:63`, пула нет), эта компиляция оплачивается **заново каждым запросом**;
prepared statements psycopg3 (порог 5 исполнений) недостижимы в принципе.

`SET jit = off`, три прогона на тёплом соединении:

| Операция | jit=on | jit=off | Ускорение |
|---|---|---|---|
| `expand_neighbors` hops=1 | 663 / 442 / 487 мс | 51 / 52 / 53 мс | **~10x** |
| `neighborhood_subgraph` hops=2 | 796 / 769 / 775 мс | 64 / 66 / 63 мс | **~12x** |
| `concept_subgraph` | 17.9 / 17.3 / 17.5 мс | 18.4 / 20.3 / 19.9 мс | нет (cost ниже порога) |
| **Суммарный бюджет БД** | **~1540 мс** | **~188 мс** | **8x** |

### Бюджет одного `/demo/api/search` (4.0–6.0 с по `curl`)

| Статья | Время | Доля |
|---|---|---|
| Внешние HTTP к LLM-шлюзу (embeddings 250–320 мс + rerank 1785–1870 мс) | ~2.1–2.2 с | ~45 % |
| PostgreSQL/AGE | ~1.3–1.5 с | ~30 % (из них ~1.2–1.3 с — чистый JIT) |
| Не атрибутировано (Python/FastAPI/пересоздание клиентов/дисперсия) | ~0.5–2 с | ~20 % |
| Сеть до БД | ~0.05 с | ~1 % |
| **Весь Python-код на пути ответа** | **2.67 мс** | **~0.05 %** |

Последняя строка — прямое измерение реального кода пакета на реальных объёмах
(55 узлов / 107 рёбер): Python-часть `neighborhood_subgraph` 0.46 мс + PII-маскирование
2.18 мс + сериализация 0.11 мс. Внутри `parse_agtype` 87 % времени — это `json.loads`,
то есть уже C. Даже при росте выдачи в 40 раз (2000 узлов / 10000 рёбер) Python-часть
составляет 33 мс.

`llm.answer` на `/demo/api/answer` — 4407 / 4531 мс при `max_tokens=280`.

### Что это значит для Rust

Закон Амдала: если переписать на Rust **весь** Python идеально, в ноль, выигрыш
составит 2.7 мс из 4000–6000 мс. Реалистичная оценка выигрыша идиоматичного
Rust-порта — **10–25 мс из ~2400–2700 мс, то есть менее 1 %**, при трудозатратах
80–150 человеко-дней на полное переписывание (8585 строк) или 30–60 на горячий путь.

Отдельно проверена зрелость Rust-экосистемы под этот стек. Зрелые замены есть
у `axum`, `pgvector` (0.4.2, автор — автор самого pgvector), `rmcp` (официальный MCP
SDK), `async-openai`, `minijinja`, `clap`, `strsim`. Паритета **нет** в трёх местах:
- **Apache AGE**: единственный крейт `apache_age` — 1932 загрузки за 90 дней, один
  мейнтейнер, с декабря 2024 только bump'ы зависимостей; официального драйвера нет
  (issue `apache/age#207` закрыт автором в 2022 без вливания в апстрим). Смягчающее
  обстоятельство: вся AGE-специфика здесь — 109 строк `core/db.py`, порт дешёвый.
- **Leiden**: `graspologic` — это уже PyO3-обёртка над Rust-крейтом `network_partitions`,
  но крейт не опубликован на crates.io (git-dep без semver и `cargo audit`).
- **MinHash**: воспроизвести `np.random.RandomState(1).randint(...)` бит-в-бит требует
  портировать MT19937 и схему отбраковки numpy, иначе изменится состав графа.

Довод «Rust опасен для контракта `/api/brain/*`» проверен адверсариально и **не устоял**:
контракт мал (19 маршрутов, ни одного `response_model`, ответы — dict-литералы), нет SSE
и WebSocket, а 227 тестов и дифференциальный харнесс «один запрос → Python и Rust →
побайтовый diff» превращают риск в pass/fail-гейт. Против Rust работает не риск, а
арифметика: оптимизировать 0.05 % запроса бессмысленно.

## Decision

1. **Не переписывать сервис на Rust ради задержек графа.** Причина отказа — не риск и
   не трудоёмкость сама по себе, а измеренный потолок выигрыша менее 1 %.
2. **Лечить измеренные причины, в порядке убывания отношения «выигрыш/цена»:**
   1. `jit=off` на соединениях к AGE (`options=-c jit=off` в `connect()` либо
      `ALTER DATABASE … SET jit=off` в `infra/memory-db/init/`) — **−1200…−1350 мс**,
      0.5 чел-дня, откат снятием переменной окружения;
   2. пул соединений `psycopg_pool` с `prepare_age` на configure-хуке — −24…−40 мс
      по p50 плюс снятие 7 каталожных round-trip'ов, и **обязательное** условие того,
      чтобы prepared statements вообще начали работать;
   3. работа с LLM-бюджетом (реранк параллельно с обходом графа / кэш эмбеддингов /
      стриминг генерации) — там лежит ~45 % времени, и язык рантайма на него не влияет;
   4. материализованная `tsvector`-колонка вместо `ts_rank` по выражению — −30 мс;
      передача эмбеддинга в запрос один раз и не текстом — −6.5…−13 мс.
3. **Требование по производительности зафиксировать до, а не после работ.** Ни один
   вариант нельзя принять или отвергнуть без целевого p95 от потребителя
   (`operator-copilot`): для realtime-суфлёра это, вероятно, 300–500 мс, и тогда даже
   2.4 с после `jit=off` — недостаточно, а решать надо LLM-часть, а не рантайм.
4. **Пересмотреть решение, если изменится профиль.** Условия пересмотра — в разделе
   Consequences.

## Consequences

- Горячий путь остаётся на Python; уходят 80–150 чел-дней, которые на стадии первой
  интеграции с потребителем стоили бы заморозки контракта и невыпущенных фич.
- Правки 1–2 не затрагивают ни маршруты `/api/brain/*`, ни схемы ответов, ни цитаты,
  ни namespaces, ни лицензию — инвариант обратной совместимости соблюдён.
- Правки уровня «материализованный tsvector» и «RRF в SQL» меняют численные детали
  ранжирования, а значит **порядок цитат-источников**. Каждая требует golden-теста на
  неизменность выдачи — цитаты приоритетнее миллисекунд.
- **Диагноз коммита `c2e59e6` был неверен.** При `jit=off` одиночный variable-path
  `[*1..2]` выполняется за 12.2–12.6 мс (1 seed) и 65.9 мс (10 seeds) — то есть не
  медленнее постадийного BFS (64 мс). Заявленные «~15 с → ~1 с» объясняются почти
  целиком JIT, а не комбинаторным взрывом обхода. Постадийный BFS в
  `graph/store.py:684` работает корректно, но усложняет код без выигрыша; после
  внедрения `jit=off` его стоит перемерить и, возможно, откатить к `[*1..hops]`.
- Property-индексы AGE (`natural_key`, `namespace`) сегодня дают −1…−2 мс: Seq Scan по
  `pc_trace` (441 строка) и `audit_event` (426) стоят ~1 мс каждый. Это вложение в рост,
  а не текущее лечение. Индексов в схеме нет вообще — только PK на `_ag_label_vertex`
  и `_ag_label_edge`.

### Условия пересмотра решения (когда Rust снова станет обсуждаемым)

1. **Инверсия профиля**: после мер 1–3 профилирование показывает > 30 % времени в Python.
   Требует одновременно убрать LLM из синхронного пути и вырастить граф на ~3 порядка.
2. **Смена целевой функции с латентности**: поставка движка на площадку заказчика
   скомпилированным бинарём (wheel читается тривиально — а CLAUDE.md требует, чтобы
   кодовая база потребителям не передавалась); жёсткий потолок RAM (сейчас RSS
   128–158 МБ, образ 443 МБ против единиц МБ и ~10–20 МБ у Rust-бинаря); хвостовые
   задержки под конкурентной нагрузкой, где GIL и 40-поточный anyio-пул становятся
   ограничением. **Ни один из этих сценариев не измерялся** — нагрузочного теста не
   было, все числа выше получены на одиночных прогонах.

## Alternatives

- **Полное переписывание на Rust (8585 строк, 80–150 чел-дней).** Отвергнуто: потолок
  выигрыша < 1 %. Технически выполнимо и риск инструментируем — но нечего выигрывать.
- **Rust только на горячем пути (server + retrieval + index + core, ~4250 строк,
  30–60 чел-дней).** Отвергнуто по той же причине: −10…−25 мс.
- **PyO3-расширение на парсинг agtype.** Отвергнуто: 87 % `parse_agtype` — это уже
  `json.loads` на C, выигрыш ~0.3 мс на запросе.
- **Граф целиком в памяти процесса (CSR).** Отложено: даёт до −137…−190 мс (весь
  остаточный бюджет графа после `jit=off`), но 5–10 чел-дней и **меняет модель
  консистентности** — после `POST /retain` снимок устаревает, что конфликтует с
  инвариантом «цитаты-источники в каждом ответе».
- **Обход по внутренним таблицам AGE обычным SQL (рекурсивный CTE).** Отложено:
  выигрыш 0…−50 мс сверх `jit=off` при жёсткой привязке к недокументированным
  внутренностям AGE (`_ag_label_vertex`, кодирование graphid, `agtype_access_operator`).
- **Замена хранилища (FalkorDB / Memgraph / Neo4j).** Отвергнуто на текущем размере
  графа. KuzuDB из рассмотрения исключён: проект заархивирован после покупки Apple.
- **Отказ от AGE в пользу обычных таблиц `nodes`/`edges` + btree + recursive CTE.**
  Не отвергнуто — заслуживает отдельного ADR. Снимает разом все три измеренные болезни
  AGE: мусорную оценку кардинальности (а с ней JIT), невозможность индексов по
  properties и Seq Scan по 15+ label-таблицам. Цена — потеря Cypher как языка запросов
  и переписывание 30 запросов в `graph/store.py`.
