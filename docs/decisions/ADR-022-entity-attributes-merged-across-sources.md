# ADR-022: Атрибуты сущности сводятся по источникам снимков, а не затираются

## Status

Proposed (2026-09-30; доработано по ревью 2026-09-30 — видимость узла и индекса,
`required` у сведения; реализовано в ветке задачи — `domain/merge.py` (сведение),
`core/kinds.py` (`sourcePriority` вида), `domain/reconcile.py` (узел графа из
сведения, `since` версии, `merge_namespace_nodes`), читатели журнала
`context/entities.py`, `context/typed.py`, `context/resolve.py`,
`domain/searchable.py`; маршрут `PUT /api/memory/namespaces/{ns}/kinds` (`merge`), CLI
`cb merge-entities`; ждёт утверждения владельца). Амендмент к MEM-ADR-020 (модель
снимков и сверки). Найдено при ревью контракта класса CRM (фича
integrations-connections); от решения зависит перенос снимков знаний CRM в память.

## Context

MEM-ADR-020 хранит версии сущности по источнику: журнал сверки
(`<snapshots>_items`) держит открытую версию каждого `(source, scope)`, и снимок
одного источника закрывает только свои версии. Но состояние сущности читалось как
**одна** версия:

- сверка переписывала свойства узла графа целиком снимком того источника, что писал
  последним (`GraphStore.upsert_entities`: `n.props = row.props`);
- перечень сущностей, индекс поиска по сущностям и канал resolve брали самую позднюю
  версию (`DISTINCT ON … ORDER BY id DESC`), typed-обход — последнюю живую.

Пример — `legal_entity` по ИНН. Учётная система пишет `name, inn, kpp, ogrn,
shortName, own`, снимок CRM — `{name, inn}`. После снимка CRM реквизиты учётной
системы не видны, пока та не перезапишет запись; какой источник «победит», зависит
от порядка записи. Маска ПДн у ИП в CRM затирает имя из учётной системы. Снимок CRM,
где компании нет, закрывал только версию CRM, но узел оставался со свойствами CRM —
реквизиты учётной системы возвращались только с её следующим изменением.

## Decision

1. **Хранение — по источнику, как и было.** Журнал уже хранит версию каждого
   `(source, scope)`; новых таблиц нет. В payload версии сущности добавлено поле
   `since` — `{"title": ts, "attributes": {имя: ts}}`: с какого `observedAt`
   источник держит каждое значение. Значение, не изменившееся с прошлой версии того
   же источника, сохраняет её время; новое или изменённое — `observedAt` снимка. Поле
   в хэш содержимого не входит: повтор снимка по-прежнему `unchanged`. У версий,
   записанных до этого решения, время значения — `valid_from` версии.

2. **Чтение — сведение версий** (`domain/merge.py`, чистая функция) всех источников,
   действующих на момент и видимых вызывающему:
   - атрибут, заданный хоть одним источником, есть в сведении; отсутствие атрибута
     или `null` в снимке другого источника его не стирает;
   - **конфликт** одного атрибута решается по атрибуту, а не по узлу:
     1. ранг источника по `sourcePriority` вида — список glob-шаблонов `source`
        (`fnmatchcase`), раньше — сильнее; источник вне списка — после всех;
     2. при равном ранге — «последний писавший» **этот атрибут**: более поздний
        `since` значения;
     3. при равенстве — `(source, scope)` по порядку строк; `id` версии различает
        только версии одного источника. Результат от порядка отправки снимков
        разными источниками не зависит;
   - `title` — по тому же правилу; заголовок, равный ключу (снимок его не дал),
     уступает любому настоящему;
   - `aliases` и `scopes` — объединение сведённых версий (у узла и строки индекса
     все сведённые версии одного класса видимости — см. п.2а); `provenance`, `source_path` и `snapshot` —
     «старшей» версии (ранг, затем более поздний `valid_from`); `sources` — все
     сведённые версии по старшинству, с цитатами;
   - интервал сведения — `[max(valid_from), min(valid_to))` сведённых версий.

   Читатели: узел графа (его пишет сверка — см. п.3; через него `recall`, `query`,
   `nodes`, обход; только класс видимости узла, п.2а), `POST /api/memory/entities:query` (`sources` в элементе, `where`
   по сведённым атрибутам), typed-обход (`sources` в элементе, снимки всех источников
   в `used.snapshots` и цитаты в `sources` ответа), канал resolve `context` (сущности,
   найденной по псевдониму или суффиксу, дочитываются все версии по ключу — ещё один
   запрос к журналу), индекс поиска по сущностям (текст эмбеддинга — из сведения
   класса видимости, п.2а).

2а. **Узел графа и строка индекса видимость не расширяют.** Читатели журнала
   (перечень, typed-обход, resolve) сводят только версии, видимые вызывающему
   (`allowedScopes`), и утечки не имеют. Узел графа и строка индекса поиска по
   сущностям одни на `(kind, key)` и видны всем, кого пропускают их `scopes`
   (`recall` фильтрует по `props.scopes`, поиск — по `scopes` строки). Поэтому в них
   сводятся только версии **одного класса видимости** — с одинаковым набором scopes
   (порядок и повторы не важны), `domain/merge.py: node_versions`:
   1. выбирается самый широкий класс из открытых: без scopes (виден всем), затем
      только scopes релевантности (без `workspace:`/`principal:`), затем со scopes
      видимости;
   2. при равной ширине — класс старшей версии (ранг, затем поздний `valid_from`);
   3. версии других классов в узел и строку индекса не попадают — их видят только
      читатели журнала тем, кому они видны.

   Пример: учётная система пишет юрлицо с `workspace:w1`, CRM — с `workspace:w2` и
   приоритетом `erp:*`: узел и строка индекса — версия учётной системы со scopes
   `[w1]`; вызывающий только с `w2` узла не видит, а в перечне получает версию CRM.
   Учётная система с `w1` и CRM без scopes: узел и индекс — публичная версия CRM
   (публичные атрибуты не пропадают у всех без `w1`), реквизиты учётной системы
   видны с `w1` в перечне и typed-обходе. Одинаковые scopes у источников (типичный
   случай) — сведение всех версий, как без этого правила.

3. **Запись узла — сведение.** Сверка сначала пишет журнал, затем для каждой
   открытой, изменённой или закрытой ею (но открытой другим источником) сущности
   записывает в узел сведение открытых версий класса видимости узла (п.2а).
   Свойства узла по-прежнему переписываются целиком — но сведением, а не снимком
   одного источника.

4. **Удаление одним источником** закрывает только его версию и его рёбра (fact_id
   рёбер сверки и прежде был привязан к источнику). Узел закрывается, только если
   сущность не держит открытой ни один источник; иначе он пересводится из
   оставшихся версий: атрибуты, которые давал только ушедший источник, уходят,
   атрибуты и связи других — остаются. Ушла версия класса видимости узла — узел
   сводится из следующего по ширине класса (и получает его scopes).

5. **Миграция узлов.** `merge_namespace_nodes` пересводит узлы всех открытых
   сущностей namespace из журнала: одной транзакцией под advisory-локом сверок
   namespace, идемпотентно, пачками по 500. Узел, удалённый через API
   (`DELETE /api/brain/nodes`), не воскрешается. Вызовы: CLI `cb merge-entities
   [--namespace …]` (все namespaces журнала по умолчанию) — однократно после
   выкатки; `PUT /api/memory/namespaces/{ns}/kinds` — после каждой смены пакетов
   (`sourcePriority` мог измениться), ответ несёт `"merge": {"nodes"}` или
   `{"error"}` (настройка сохраняется, повтор `PUT` доделает). Журнал миграции не
   нужен: читатели журнала сводят версии на чтении, у старых версий `since`
   выводится из `valid_from`. `PUT …/kinds` пересводит узлы, только если
   `sourcePriority` видов действующего каталога отличается от того, по которому
   узлы namespace сведены в последний раз (иначе `"merge": {"nodes": 0,
   "skipped": true}`): пересведение синхронное и идёт по всему namespace.
   Отпечаток — `sourcePriority` видов (`{kind: [шаблоны]}`) в колонке
   `merged_priority` настроек namespace (`CB_NAMESPACE_SETTINGS_TABLE`, добавляется
   аддитивно); пишется в той же транзакции, что и успешное пересведение
   (`PUT …/kinds` и `cb merge-entities`). Сравнение именно с ним, а не с настройкой
   до `PUT`: новая версия пакета, включённого без версии, меняет каталог без смены
   настройки, а после `"merge": {"error"}` отпечаток остаётся прежним — в обоих
   случаях повтор `PUT` пересводит узлы. Отпечатка ещё нет (namespace не сводился) —
   `PUT` пересводит.

   Отпечаток описывает **все** узлы namespace, поэтому его сбрасывает и сверка
   снимка. Сверка сводит узлы своих сущностей по каталогу, который прочитала сама;
   если `sourcePriority` этого каталога отличается от отпечатка, она в той же
   транзакции под advisory-локом сверок namespace пишет в `merged_priority`
   `NULL`, и следующий `PUT …/kinds` пересводит весь namespace. Иначе отпечаток
   лгал бы: после регистрации новой версии пакета без версии сверка переписывает
   узлы по новому приоритету, а откат `PUT packages=["pack@1"]` (или версия,
   возвращающая прежний приоритет) видит отпечаток старого приоритета и
   пропускает пересведение. Сравнение идёт под локом, поэтому закрыта и гонка
   «сверка прочитала каталог до `PUT`, а записала после его пересведения». Со
   стороны `PUT` то же: отпечаток он читает в одной транзакции с пересведением и
   `mark_merged`, после `pg_advisory_xact_lock` сверок namespace (в той же сессии
   лок берётся повторно). Иначе `PUT` мог бы прочитать закоммиченный отпечаток,
   пока сверка по другому каталогу уже записала узлы, но ещё не сбросила его, и
   ответить `skipped` при узлах, сведённых не по настройке; без
   `searchable`-видов `reindex_namespace` лок не берёт, и защитить сравнение было
   бы нечем (TASK-001179). Сверка
   по тому же `sourcePriority` и `dryRun` отпечаток не трогают. Колонку
   отпечатка до `ensure_schema` (таблица настроек старше этого решения) сверка
   считает пустой отпечатком и не падает; DDL колонки выполняется до транзакций
   пересведения (`put_settings`, начало `cb merge-entities`), не внутри них.

   **Заметка выкатки.** У namespaces, сведённых до появления отпечатка, его нет,
   поэтому первый `PUT …/kinds` после выкатки синхронно пересводит весь namespace.
   Чтобы не держать запрос `PUT` на больших базах, заранее выполнить
   `cb merge-entities` (пишет отпечаток для каждого namespace журнала).

   Миграция, как и сверка, **переписывает свойства узла целиком** сведением журнала:
   свойства, которые попали в узел сущности сверки мимо журнала (например, ручной
   правкой графа), при миграции теряются. Так было и до этого решения — сверка
   всегда переписывала `props` узла снимком; миграция лишь делает это для всех
   открытых сущностей namespace сразу.

6. **`required` — у сведения, а не у вклада.** Вклад источника может быть
   частичным: CRM даёт `{inn}` юрлица, имя которого держит учётная система. При
   разборе снимка (строгий режим) у вклада проверяются вид, ключ, типы и прочие
   ограничения схемы `attributes`, кроме `required` верхнего уровня
   (`check_entity(partial=True)`). `required` проверяется после записи журнала в той
   же транзакции у сведения **всех** открытых версий сущностей снимка (любых
   классов видимости: полнота сущности — не вопрос видимости), только у видов с
   `required` в строгом режиме — ещё один запрос к журналу. Нет обязательного
   атрибута ни в одном источнике — `AttributesError` (HTTP `422`, как и прежде у
   нарушений схемы), сверка откатывается целиком. `null` в сведении — отсутствие
   атрибута. Сверка, которая только закрывает версию своего источника, `required`
   оставшихся версий не проверяет: сведение может стать неполным, когда уходит
   источник обязательного атрибута; следующий снимок оставшегося источника без
   этого атрибута будет отвергнут.

   Косвенный канал: пишущий в namespace по ответу сверки (в том числе `dryRun`)
   узнаёт, задан ли обязательный атрибут сущности хоть одним другим источником,
   включая версии с недоступными ему scopes, — только факт наличия, не значение.
   Принято: право записи в namespace выдаётся доверенным производителям снимков.

## Consequences

- Потребитель видит полную карточку сущности из всех источников; порядок прихода
  снимков на результат не влияет. Контракт расширен аддитивно: `sourcePriority` вида
  в пакете, `sources` в элементах `entities:query` и typed-обхода, `merge` в ответе
  `PUT …/kinds`. Прежние поля (`source`, `scope`, `snapshot_id`, `source_path`,
  `snapshot`) остались — теперь это старшая из сведённых версий.
- Сверка делает ещё один запрос к журналу (открытые версии тронутых сущностей) —
  тот же, что уже делал индекс поиска; перечень сущностей — два запроса на страницу
  (позиции, затем их версии); канал resolve — до четырёх запросов вместо трёх.
- `sourcePriority` — данные пакета. Пакеты иммутабельны: смена приоритета — новая
  версия пакета и `PUT …/kinds`. Шаблоны — по полю `source` снимка, поэтому имена
  источников инсталляции стоит договорить с производителями снимков (например,
  `erp:*`, `crm:*`).
- **Узел графа и строка индекса при разных scopes источников** показывают сведение
  одного класса видимости (п.2а): `recall`, `nodes` и поиск по смыслу могут показать
  вызывающему меньше атрибутов, чем перечень и typed-обход, но никогда — чужие.
  Полную карточку в пределах своей видимости вызывающий получает из перечня
  сущностей и typed-обхода.
- **`sourcePriority` для сущностей из учётной системы и CRM обязателен на практике.**
  Без него конфликт имени решает «последний писавший»: снимок CRM с маской ПДн в
  имени ИП, наблюдённый позже, перебьёт имя из учётной системы. Пакет с
  `legal_entity`, который пишут обе системы, должен задать
  `"sourcePriority": ["erp:*"]` (или шаблон источников учётной системы инсталляции).
- `PUT …/kinds` со сменой `sourcePriority` пересводит узлы всего namespace
  синхронно, одной транзакцией; на больших базах — дольше обычного `PUT`.
- Атрибуты сравниваются целиком: вложенные объекты не сливаются поле за полем.

## Alternatives

- **Слияние свойств узла при записи (`SET n.props = n.props + row.props`)** —
  атрибуты не терялись бы, но их нельзя было бы убрать: снимок, где атрибута больше
  нет, не отличить от снимка другого источника, где его никогда не было; закрытие
  сущности одним источником оставляло бы его атрибуты навсегда. Отвергнуто.
- **Только приоритет источников**, без «последнего писавшего», — источники вне
  списка сравнивались бы порядком записи. Отвергнуто: нужен детерминизм и без
  настройки пакета.
- **«Последний писавший» по узлу (по `valid_from` версии)** — смена любого
  атрибута источником перебивала бы все его атрибуты, в том числе не менявшиеся.
  Отвергнуто в пользу `since` по атрибуту.
- **Время атрибута из истории версий на чтении** — без нового поля, но каждое чтение
  тянуло бы всю историю версий сущности. Отвергнуто: `since` считается один раз при
  записи.
- **Объединение scopes версий в узле** (первая редакция этого решения) — узел видят
  вызывающие с любым из scopes источников, и через него видны атрибуты всех
  источников (fail-open). Отвергнуто на ревью.
- **Класс видимости старшей версии** (без предпочтения широкого класса) — утечки
  нет, но при старшей версии с `workspace:w1` публичные атрибуты другого источника
  пропадают из `recall` у всех без `w1`. Отвергнуто в пользу самого широкого класса.
- **Узел на класс видимости** (несколько узлов одной сущности) — полное сведение в
  каждом классе, но меняет идентичность узла графа (`(kind, key)`), рёбра и все
  читатели графа. Отвергнуто как несоразмерное; можно вернуться, если понадобится.
- **`required` у вклада снимка** (первая редакция) — частичный вклад CRM
  отвергался при уже записанном полном вкладе учётной системы. Отвергнуто на ревью.
- **Приоритет в настройке namespace, а не в пакете** — ближе к инсталляции, но
  разводит описание домена и правило его сведения по двум местам. Можно добавить
  позже как переопределение, не ломая формат пакета.

## Открытые вопросы мейнтейнеру

1. Выбор класса видимости узла (п.2а): самый широкий класс (текущее) показывает в
   `recall` публичную версию и тем, кто видит полную; альтернатива — класс старшей
   версии. Утечки нет в обоих вариантах; вопрос — какая неполнота `recall`
   предпочтительнее.
