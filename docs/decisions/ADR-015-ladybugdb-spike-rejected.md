# ADR-015: LadybugDB как встраиваемая замена PostgreSQL — отклонено по результатам спайка

## Status

Proposed (2026-07-28). Закрывает вариант, предложенный как основной в
[ADR-014](ADR-014-delivery-form-storage-not-language.md) («встраиваемое хранилище —
единственный путь к честному одному файлу») и одобренный владельцем к проверке.

## Context

ADR-014 установил: форму поставки определяет хранилище, а не язык, и единственная
архитектура, где «один файл» становится честным, — отказ от AGE и pgvector в пользу
встраиваемого движка. Кандидат — **LadybugDB** (MIT, форк Kuzu после архивации последнего
Apple 2025-10-10). Владелец решил проверить.

Проведён эмпирический спайк на `ladybug 0.18.3`: пять параллельных проб с прогоном
реального кода. Ключевые результаты перепроверены вручную минимальными репро.

### Что оказалось лучше ожиданий

- **FTS-индекс мутабелен** — главная гипотеза о блокере (наследие Kuzu, где индекс был
  иммутабелен) **опровергнута**. Вставка, удаление и обновление отражаются немедленно.
- **Русский стеммер snowball работает штатно:** «договор» находит «договоры», «договором»,
  «договоров». BM25 настоящий, параметры `k`/`b` настраиваются, есть conjunctive-режим.
- **Векторный индекс мутабелен**, метрики COSINE/L2/IP, размерность контролируется.
- **`MERGE` даёт честную upsert-семантику** openCypher — единственный из шести проверенных
  пунктов схемной модели, прошедший без оговорок.
- **Вектор + FTS + обход графа + RRF собираются в ОДИН Cypher-запрос** (сегодня это три
  запроса и слияние в Python), причём выдача сразу несёт `source_path` — инвариант
  цитат-источников сохраняется.

### Блокеры

**1. Расширений нет в артефакте — они скачиваются по сети.** Проверено вручную: пакет
занимает 19,3 МБ, файлов FTS и vector внутри **нет**; после `INSTALL FTS` они появились
в `~/.lbdb/extension/osx_arm64`, скачанные с единственного CDN `extension.ladybugdb.com`.
Расширения для релиза v0.17.1, которому два месяца, **уже удалены с CDN (404)**.
Это уничтожает оба мотива сразу: и «поставка одним файлом», и «закрытый контур без
интернета». Прод-сервер в РФ без доступа к этому CDN не создаст ни один индекс.

**2. Составной первичный ключ невыразим — ломается изоляция баз знаний.** Проверено вручную:
```
CREATE NODE TABLE n(natural_key STRING, namespace STRING, PRIMARY KEY(natural_key, namespace))
→ Parser exception: extraneous input ',' expecting {')', SP}

CREATE (x:m {natural_key:'concept:тариф', namespace:'банк'})
CREATE (x:m {natural_key:'concept:тариф', namespace:'карта-москвича'})
→ Runtime exception: Found duplicated primary key value concept:тариф,
  which violates the uniqueness constraint of the primary key
```
Один и тот же `natural_key` в двух namespace физически не помещается в граф. Это ровно
пример из `CLAUDE.md` («банк» и «карта москвича») и **приоритет продукта №3**.

**3. SIGSEGV на записи при пользовательских стоп-словах.** Проверено вручную, код возврата
139 (128+11). FTS-индекс, созданный с любым пользовательским списком стоп-слов, роняет
процесс на любой записи в индексируемую таблицу. Русские стоп-слова задать иначе нельзя:
имя `'russian'` не принимается, `.txt` не грузится, а `'default'` — английский список.
То есть «мутабельный FTS» и «русские стоп-слова» в 0.18.3 взаимоисключающи.

**4. Модель конкурентности несовместима с архитектурой сервиса.** Одна БД = один
процесс-писатель, жёсткий файловый лок; `uvicorn --workers 2` физически невозможен.
Read-only процессы открываются, но видят **снимок на момент открытия** и никогда не видят
последующих записей — новый `Connection` не помогает, только переоткрытие `Database`
(~52 мс на базе 79 МБ, при том что сам обход графа — 1,9 мс). Нынешняя модель
«соединение на запрос» (11 мест в `server/app.py`) под нагрузкой даёт **19 % отказов**
на `/retain`. А конкурентный `MERGE` в один узел — ровно паттерн entity resolution —
роняет процесс SIGSEGV в 5 прогонах из 6.

**5. Свободные свойства не поддерживаются.** Запись свойства, которого нет в схеме, —
жёсткая `Binder exception`, а не NULL. `MAP(STRING,STRING)` однороден (типы теряются),
индексировать его нельзя, фильтровать — только через `list_contains(map_extract(...))`.
Тип `JSON` есть, но его функции живут в скачиваемом расширении. Произвольный frontmatter,
на котором построен ingest, невыразим без `ALTER TABLE` на каждый новый ключ.

**6. Bus factor = 1.** Из 968 коммитов после форка **770 (79,5 %) сделал один человек**.
Ни один из шести core-разработчиков Kuzu не написал в Ladybug ни строки; `CODEOWNERS`
на `src/storage` до сих пор указывает на разработчика, ушедшего в Apple. Issue **#377**
(«нельзя писать в таблицу с HNSW-индексом» — ровно наш `/retain`) открыт 107 дней
с нулём комментариев. Открытых багов класса crash за полгода — 12, и они бьют ровно
по FTS, вектору и многопроцессному доступу. Имя пакета сменилось трижды за девять месяцев
(`kuzu` → `lbug` → `real_ladybug` → `ladybug`), формат на диске — трижды за восемь,
даунгрейд невозможен.

## Decision

1. **Не переводить memory-service на LadybugDB.** Причина не в одном дефекте, а в том, что
   блокеры лежат в разных плоскостях: продуктовой (изоляция KB невыразима), поставочной
   (расширения качаются из сети — оба мотива перехода аннулированы), эксплуатационной
   (модель конкурентности несовместима) и организационной (bus factor 1 на фундаменте
   коммерческого продукта).
2. **Остаться на PostgreSQL + AGE + pgvector.** Вопрос встраиваемого хранилища вернуть
   к рассмотрению не раньше, чем (а) расширения начнут поставляться в артефакте,
   (б) появится составной или суррогатный первичный ключ, (в) у проекта появится второй
   активный мейнтейнер. Ни одно из трёх не находится под нашим влиянием.
3. **Забрать из спайка то, что применимо к нынешнему стеку** — см. Consequences.

## Consequences

- Цель «честный один файл» остаётся недостижимой. В силе остаётся вывод ADR-014: форму
  поставки закрывает сборка (PyInstaller собирает нынешний сервис в один файл 48,5 МиБ,
  контракт проходит), а двухкомпонентность сохраняется.
- **Переносимая находка №1: HNSW не окупается на нашем масштабе — ни в Ladybug, ни, судя
  по всему, у нас.** В спайке полный перебор оказался быстрее индекса на всех измеренных
  объёмах при recall = 1,0, а на 300 000 векторов HNSW деградировал до 380–920 мс против
  24 мс у перебора. Это согласуется с ранее замеренным на стенде: планировщик PostgreSQL
  **не выбирает** `chunks_emb_hnsw` при 134 строках и идёт Seq Scan. Стоит проверить,
  не тратим ли мы на поддержание индекса больше, чем он экономит.
- **Переносимая находка №2: слияние каналов в один запрос.** Спайк показал, что вектор,
  FTS и обход графа собираются в один запрос вместе с RRF. У нас это три round-trip'а
  и слияние в Python. Приём применим к PostgreSQL и заслуживает отдельной оценки —
  с обязательным golden-тестом, потому что перенос RRF в SQL меняет порядок цитат.
- Спайк стоил день и снял вариант, который в ADR-014 назывался единственным путём к цели.
  Это дешевле, чем узнать то же самое на третьем месяце переписывания слоя хранения.

## Alternatives

- **Дождаться зрелости Ladybug.** Не отвергнуто, но не планируется: три условия возврата
  перечислены в Decision, ни одно от нас не зависит.
- **Другой встраиваемый движок.** CozoDB спит с 2024-12-04; SurrealDB embedded под BSL 1.1
  до 2030 года и ломает инвариант обратимости; PGlite — обёртка AGE версии 0.0.5
  в single-user режиме. Кандидатов, закрывающих граф + вектор + русский FTS одной
  встраиваемой библиотекой под пермиссивной лицензией, на 2026-07-28 не осталось.
- **Собрать своё хранилище** (SQLite + рекурсивные CTE для графа + `usearch` для векторов
  + FTS5). Технически возможно и снимает зависимость от чужого проекта, но это не спайк,
  а отдельный продукт внутри продукта, и он перечёркивает openCypher как язык запросов —
  31 запрос из `graph/store.py` переписывается в код. Не рекомендуется без отдельного
  решения владельца.
