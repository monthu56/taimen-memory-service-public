# ADR-006: Иерархическая суммаризация до уровня узла/статьи — summary-first retrieval

## Status

Proposed (2026-07-23; предложено по разбору CodeAlive Context Engine, ожидает
утверждения владельца). Часть пакета улучшений retrieval ADR-005…008 —
принимаются независимо друг от друга.

## Context

Сейчас краткое описание существует только на уровне **сообщества** графа
(communities, Phase 3: `community_name` в `_fmt_neighbor` и `subgraph_to_text`).
У отдельного узла/статьи есть `title`/`label`, но нет краткого LLM-описания
рядом с полным телом. Retrieval кладёт в контекст сырые чанки (`_build_context`)
и сериализованный подграф под токен-бюджет (`subgraph_to_text` в
`retrieval/expansion.py`).

CodeAlive Context Engine держит краткое описание рядом с полным телом каждого
артефакта, что позволяет retrieval отдавать «summary-first»: сначала сжатые
описания, полный текст — только для реально отобранных. У нас это дало бы более
плотный и дешёвый по токенам контекст, особенно для обзорных запросов «как
связано X с Y».

## Decision

1. **Хранить краткое `summary` (1–3 предложения) на уровне узла** (статья/
   сущность), генерируемое LLM при ingest.
2. **Не перебилливать неизменённое**: генерация ключуется по content-hash тела
   (переиспользовать паттерн `ExtractionCache` из `ingest/cache.py` — LLM-вывод
   не версионируется чанкером, namespace по модели LLM).
3. **Где хранится**: свойство узла графа (`props.summary`) и опционально в `meta`
   заголовочного чанка. Origin-совместимо: агентские write-back узлы могут нести
   `summary` в свойствах (инвариант 5 не затрагивается — HTTP по-прежнему пишет
   только origin='agent').
4. **Retrieval**: под токен-бюджетом `subgraph_to_text`/`_build_context` сначала
   отдаёт `summary` узлов; полный текст чанков тянется только для top-N после
   реранка (связка с ADR-005). Иерархия: узел → сообщество.
5. **Аддитивно и за флагом** `CB_SUMMARY_ENABLED`: новое поле `summary` в ответах
   узловых маршрутов (`GET /nodes/{key}`) — расширение контракта, не слом
   (инвариант 2).

## Consequences

- Обзорные ответы дешевле по токенам и плотнее по релевантному — усиление
  приоритета №2 (источник показывается сжато, оригинал — по ссылке).
- +стоимость LLM на ingest; митигируется кэшем по content-hash (повторный ingest
  неизменённого vault не перегенерирует).
- `summary` привязан к тому же хэшу тела, что и чанки, — устаревание
  контролируемо (тело изменилось → summary перегенерируется).
- Достраивает существующую community-суммаризацию до полной иерархии.

## Alternatives

- **Экстрактивное summary (первые N предложений)** — дёшево, но хуже для
  структурированных заметок с frontmatter; оставлено как возможный fallback
  при отключённом LLM.
- **Только community-summary (статус-кво)** — отклонено: не покрывает узловой
  уровень, где и происходит основной retrieval.
- **Summary на лету при каждом запросе** — отклонено: дорого и недетерминированно,
  хуже кэшируемой генерации на ingest.
