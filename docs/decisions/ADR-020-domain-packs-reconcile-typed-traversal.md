# ADR-020: Доменные пакеты видов, reconcile снимков источников и типизированный обход с as_of

## Status

Proposed (2026-09-23; амендмент 2026-09-23 — см. раздел «Амендмент: реальные снимки
SNAPSHOT.md»; второй амендмент 2026-09-23 — «Амендмент: маршруты ядра, индекс ключей,
повтор отложенных связей»; третий амендмент 2026-09-23 — «Амендмент: канал resolve
компилятора контекста»; четвёртый амендмент 2026-09-25 — «Амендмент: typed-контекст
разрешает якоря через resolve_candidates»; пятый амендмент 2026-09-25 — «Амендмент:
пакетное разрешение якорей и обход без просмотра всего графа»; реализовано в ветке задачи — `core/kinds.py`,
`core/packs/default.json`, `domain/registry.py`, `domain/reconcile.py`,
`context/typed.py`, маршруты `/api/memory/{packages,namespaces/{ns}/kinds,reconcile,
context/typed}`; ждёт утверждения владельца). Суперпроект: TAI-ADR-0042 п.1, 2, 4, 5
(контекст задачи из базы знаний, P1a). Развивает ADR-016 (факты с валидностью,
Context Compiler) и ADR-019 (видимость по principal).

## Context

Движок product-neutral, но бизнес-онтология vault была зашита кодом
(`core/ontology.py`: список типов и шаблоны `BIZ-/T-/Q-/M-NNN`). Контекст задачи
(TAI-ADR-0042) требует, чтобы потребитель приносил свой домен — виды сущностей,
связи, шаблоны идентификаторов — данными, без правки движка. Кроме того:

- источники (трекер, репозиторий, CRM) умеют отдавать только **полный снимок**
  состояния; движок должен сам понять, что открылось, изменилось и пропало,
  не теряя истории и не удаляя ничего;
- Context Compiler расширял граф через `expand_neighbors` без учёта валидности
  рёбер: закрытый факт участвовал в контексте, `as_of` на обход не влиял;
- для evidence задачи нужен точный список сущностей, фактов и снимков, из которых
  собран контекст.

## Decision

1. **Доменный пакет — данные.** `{name, version, kinds[{kind, naturalKey, aliases,
   kindAliases, idPatterns, attributes}], relations[{relation, fromKinds, toKinds,
   temporal, cardinality}]}` (амендмент: `version` числом, `aliases`, `kindAliases`,
   `cardinality`).
   - `naturalKey` — JSON Schema строки ключа или шаблон ключа с плейсхолдерами
     `<name …>` / `{name}`;
   - `aliases` — формы **естественного ключа** сущности (шаблоны), `kindAliases` —
     синонимы **имени вида** (`ticket` → `issue`), приводятся к каноническому имени
     при записи и в якорях;
   - `idPatterns` — регулярные выражения извлечения идентификаторов из текста
     (группа `id` или всё совпадение);
   - `attributes` — JSON Schema атрибутов. Валидатор — встроенное подмножество JSON
     Schema (type, enum, const, pattern, min/maxLength, minimum/maximum, properties,
     required, additionalProperties: bool, items) без новой зависимости; прочие
     ключевые слова игнорируются;
   - `temporal: true` (по умолчанию) — у фактов связи есть интервал валидности;
     замена 1:1 при сверке — только у `cardinality: one` (амендмент).
   Имена видов и связей — `[a-z][a-z0-9_]{0,62}` (становятся AGE-меткой/типом ребра).
   Базовые виды `document`, `entity`, `fact` есть всегда и не переопределяются.
2. **Реестр пакетов** — таблица `CB_DOMAIN_PACKS_TABLE` (`name, version, spec,
   spec_hash`). Версия иммутабельна: повтор той же версии с тем же содержимым —
   `unchanged`, с другим — `409`. Регистрация — **service scope**: ключ реестра
   `"service": true`, IAM-scope `memory:service` (новый; назначается потолком
   service account в IAM), full-access ключ или локальный режим. Чтение пакетов —
   любому аутентифицированному вызывающему (это схема, не данные tenant).
3. **Пакет по умолчанию.** Бывший код `core/ontology.py` переехал данными в
   `core/packs/default.json` (встроенный пакет `default@1`, имя зарезервировано).
   `ontology.is_natural_id/id_type` — natural-id resolver — берут шаблоны из
   `idPatterns` каталога (по умолчанию — из `default`, либо из переданного
   каталога namespace); `CORE_TYPES`/`ID_PATTERNS` вычисляются из пакета.
4. **Строгий режим — настройка namespace** (`CB_NAMESPACE_SETTINGS_TABLE`,
   `PUT /api/memory/namespaces/{ns}/kinds {strict, packages}`; право записи в
   namespace). `packages=null` — только `default` (амендмент: пакет действует лишь
   там, где явно включён); список — ровно перечисленные (`name` или `name@version`), при совпадении имён
   побеждает стоящий раньше. `strict=true` — сущность неизвестного вида, ключ или
   атрибуты вне схемы вида отвергаются (`UnknownKindError`/`AttributesError` →
   HTTP `422`). `strict=false` (по умолчанию) — прежнее поведение: любой вид.
   Проверка стоит на путях записи агента: `GraphStore.write_fact` (facts, retain,
   documents) и `FactStore.ensure_entity` (сущности и концы фактов наблюдений,
   reconcile) через `GraphStore.kind_guard`, подключаемый
   `domain.registry.attach_kind_guard`. Контентные узлы `text`-assertion и
   vault-ingest не проверяются (не сущности домена / не HTTP-запись).
5. **reconcile(source, scope, snapshot)** — `POST /api/memory/reconcile`
   (формат снимка, журнал и связи — по амендменту ниже; текст этого пункта описывает
   исходную версию P1a).
   Журнал `CB_SNAPSHOTS_TABLE` (снимки: результат по `(namespace, source,
   snapshot_id)`) и `<table>_items` (версии сущностей и фактов источника с
   `valid_from/valid_to`, `superseded_by`, содержимым). В одной транзакции под
   advisory-локом `(namespace, source)`:
   - сущность: новая → узел (`origin='agent'`) + версия; изменилась (хэш
     содержимого) → старая версия закрыта с `superseded_by`, узел обновлён;
     пропала → версия закрыта, узел получает `valid_to`, если его не держит
     открытым другой источник;
   - факт `(subject, relation, object)`: новый → `assert_fact` (`evidence=asserted`,
     `valid_from=taken_at`, `snapshot_id`); изменились атрибуты или temporal-замена →
     новый факт с `supersedes`, старый закрыт; пропал → `invalidate_fact`;
   - ничего не удаляется; ответ — `opened/closed/unchanged/superseded` (итого и
     по сущностям/фактам); изменившийся элемент — и закрыт, и открыт.
   Идемпотентно по `(namespace, source, snapshot_id)`: повтор возвращает
   сохранённые счётчики с `duplicate: true`. Снимок с `taken_at` раньше последнего
   принятого — `409` (история не переписывается задним числом). Виды и схемы
   проверяются до записи — снимок принимается целиком или не меняет ничего.
6. **Типизированный обход** — `POST /api/memory/context/typed` (`context/typed.py`):
   якоря `{kind?, value}` разрешаются по порядку: точный `natural_key` (и
   `<kind>:<value>` — ключ наблюдений) → псевдоним сущности → `idPatterns`;
   семантический добор — только при явном `allow_semantic`, с `evidence: inferred`
   (id_pattern — `extracted`, точные — `asserted`). Шаги `traverse[{relation,
   direction in|out|both, depth ≤ 5, limit ≤ 200, from anchors|previous}]` — BFS
   только по рёбрам, валидным на `as_of` (`valid_from ≤ t < valid_to`; без `as_of`
   — `valid_to IS NULL`), без `evidence_lost`. Сущность видна на `as_of` по версии
   журнала снимков (атрибуты — из неё), без журнала — по своему интервалу.
   Ответ: разделы по видам, факты, `used{entities, facts, snapshots}`, `sources`,
   `trace_id` (трейс — в той же таблице трейсов компиляций). Видимость MEM-ADR-019
   и PII-барьер — как у `/api/memory/context`.

## Амендмент: реальные снимки SNAPSHOT.md (2026-09-23)

Ревью P1a: на реальных снимках производителя (`SNAPSHOT.md` и пакет
`software-delivery.yaml` суперпроекта, TAI-ADR-0042 п.2, п.8) сверка давала 0 фактов и
`taken_at = now`, связь на сущность другого снимка — 500. Контракт производителя
первичен, поэтому сервис принимает его формат как есть.

1. **Формат снимка** — документ `{pack, source, scope (строка), snapshotId, observedAt,
   entities[{kind, key, title, attributes, provenance}], relations[{relation,
   from{kind,key}, to{kind,key}, attributes}]}`. Прежний формат P1a
   (`facts[{subject,object}]`, `taken_at`, обёртка `{source, snapshot, scope}`) снят —
   он не выпускался в master. `observedAt` обязателен — это время снимка
   (`valid_from/valid_to` версий). `provenance` входит в содержимое и хэш: его смена —
   supersede; цитата сущности — `repo@sha:path:line`.
2. **HTTP.** Тело `POST /api/memory/reconcile` — плоский документ снимка; namespace —
   полем `namespace` или `?namespace=` (расхождение — 400); `scopes` — scopes
   видимости MEM-ADR-019 из запроса ядра, пишутся в `props.scopes` узлов и `r.scopes`
   рёбер снимка (входят в хэш содержимого). `pack` снимка должен быть включён в
   namespace (иначе 400).
3. **Журнал по `(source, scope)`**, как в SNAPSHOT.md: идемпотентность по
   `(namespace, source, scope, snapshotId)`, отказ устаревшего — по
   `(namespace, source, scope)`; сверка закрывает только своё `(source, scope)`.
   Идентичность: сущность — `(kind, key)` (колонка `kind` в `_items`), связь —
   `(relation, from, to)`. Таблицы P1a не выпускались, схема изменена без миграции.
4. **Отложенные связи.** Связь, у которой конца нет в графе, хранится в журнале с
   `graph_ref = ''` (индексы `ref_from/ref_to`) и материализуется ребром, когда конец
   появляется: при сверке снимка, впервые открывшего сущность (связи любых
   источников), или при следующей сверке своего источника. `valid_from` ребра — время
   снимка, где связь наблюдалась. Ответ: `relations.pending/resolved`. Выбрано вместо
   узлов-заглушек: заглушка — сущность, которой не утверждал ни один источник, она
   видна обходу и требует отдельного закрытия. Сверки namespace сериализуются одним
   advisory-локом — разрешение пересекает источники.
5. **Пакеты.** `version` числом приводится к строке. `aliases` — шаблоны форм ключа:
   плейсхолдер берётся из атрибутов, затем из частей ключа по шаблону `naturalKey`
   (endpoint `GET /runs/{}` с атрибутом `path` → `/runs/{run_id}`; `adr` `TAI-0042` →
   `ADR-0042`, `TAI-ADR-0042`); формы пишутся в `props.aliases`, якорь обхода
   разрешается по ним. Форма без плейсхолдера отвергается (подсказка про
   `kindAliases`). Строгий режим проверяет форму ключа по шаблону и **связи**:
   объявлена ли связь, входят ли канонические виды концов в `fromKinds/toKinds`
   (`UnknownRelationError` → 422).
6. **Пакет действует только в namespace, где явно включён**; без настройки — только
   `default`. Регистрация пакета ни на один namespace не влияет.
7. **Temporal.** fact_id ребра сверки — `(namespace, source, scope, связь, снимок
   открытия версии)`: закрытие фактом одного источника не трогает факт другого, а
   ребро создаётся (`CREATE`), так что повтор с тем же `valid_from` не переоткрывает
   закрытое. Связь по умолчанию — набор (`cardinality: many`): закрываются пропавшие
   пары; замена 1:1 с `supersedes` — только при `cardinality: one`.
8. **Производительность.** Узлы, закрытия и рёбра пишутся батчами `UNWIND` по виду/
   связи, `MATCH` — с меткой вида; на таблицах меток сверки — GIN-индекс по
   `properties` (AGE транслирует `{natural_key, namespace}` и `{fact_id}` шаблона в
   `@>` — index scan и внутри UNWIND); журнал — `executemany`. Замер
   (тест `TestPerformance`, тестовая БД): снимок 1001 элемент — ~0.4 с, дифф с
   80 изменениями — ~0.1 с.

Последствия амендмента: `assert_fact` больше не используется сверкой (параметры
`attributes/snapshot`, добавленные P1a, сняты); `GraphStore.set_node_validity` заменён
батчевыми `upsert_entities/close_entities`. Ребро на сущность, которую источник
позже закрыл, остаётся открытым у источника связи; обход его не проходит, потому что
конец не виден на `as_of`. Клиент `platform-memory-client`: `reconcile(snapshot, *,
namespace, scopes)` вместо `reconcile(source, snapshot, *, namespace)`.

## Амендмент: маршруты ядра, индекс ключей, повтор отложенных связей (2026-09-23)

Замечания ревью P1a, не блокировавшие мерж, и амендмент TAI-ADR-0042 от 2026-09-23
(«память — только через Control Plane»).

1. **Маршруты ядра.** `POST /api/memory/reconcile`, `POST/GET /api/memory/packages`,
   `GET /api/memory/packages/{name}` и `GET/PUT /api/memory/namespaces/{ns}/kinds`
   вызывает только identity ядра. **Identity ядра — service scope**, единый контракт
   для всех служебных маршрутов памяти (решение владельца 2026-09-23 по ревью
   TASK-000305): IAM-scope `memory:service` (уже есть в audience `memory-service` и в
   потолке service account ядра; ядро запрашивает его в общем токене вместе с
   `memory:read`/`memory:write`/`memory:tenants`) или ключ реестра `CB_API_KEYS` с
   `"service": true`. Отдельного scope ядра нет: `memory:core` из первой редакции
   амендмента отвергнут — его не было ни в audience, ни в потолке, ни в запросе ядра,
   и при включённом ограничении ядро получило бы `403`. Ограничение настраиваемое и
   по умолчанию **выключено** (существующие инсталляции и локальный режим не
   меняются):
   - `CB_CORE_ONLY=true` включает ограничение без списка: проходит только service
     scope;
   - `CB_CORE_IDENTITIES` — дополнительно доверенные метки вызывающих через запятую:
     `name` ключа реестра, `base`/`pii-full` для legacy-ключей,
     `iam:<principal_type>:<principal_id>` для IAM-токена (та же метка, что в журнале
     доступа); непустой список тоже включает ограничение, service scope проходит и
     тогда.
   При включённом ограничении прочие вызывающие получают `403` **даже с грантом на
   namespace** и даже с full-access ключом (неявное право регистрации пакетов у
   ключа с записью во все базы identity ядра не делает — нужен явный `"service":
   true`); `memory:write`/`memory:tenants` без `memory:service` — тоже `403`.
   Локальный режим без аутентификации ядро не опознаёт — `403`, если метка `default`
   не перечислена явно (fail closed). Под ограничением и **`GET /packages`**: каталог
   пакетов агенты и люди получают через Control Plane, а не из памяти напрямую.
   Ограничение — дополнительное условие, а не замена: ядру по-прежнему нужны право
   записи в namespace (reconcile, `PUT …/kinds`) и чтения (`GET …/kinds`).
   Остальные маршруты `/api/memory/*` и `/api/brain/*` ограничение не затрагивает.
   Проверка — `app._authorize_core` по `CallerGrants.service` и метке вызывающего.
2. **Индекс для выборок по ключам.** `existing_keys` и `close_entities` фильтровали
   `n.natural_key IN $keys`: AGE исполняет `IN` перебором списка на каждой строке
   метки (seq scan; 1000 ключей на ~30k узлов — ~1.3 с на выборку), GIN по
   `properties` не помогает. Выборка переписана на `UNWIND $keys AS k MATCH (n:<вид>)
   WHERE n.natural_key = k AND n.namespace = $ns`, а на метках узлов сверки
   `ensure_label_index` добавляет **hash-индекс по выражению `natural_key`** (то
   выражение, в которое AGE транслирует `n.natural_key`). Замер (тестовая БД, 1000
   ключей): на 30k узлах — ~15 мс (планировщик выбирает hash join с одним seq scan),
   на 300k — ~3 мс index nested loop по hash-индексу против ~100 мс без него; снимок
   ~1000 элементов со связями на узлы графа 30k — ~1 с (`TestPerformance`).
   Отвергнуто: `UNWIND` + шаблон `{natural_key: k, namespace: $ns}` через GIN (вхождение
   `namespace` общее у всех узлов — каждый поиск читает его posting list, 2.1–2.5 с);
   B-tree по выражению (предел размера записи ~2.7 КБ, длина ключа не ограничена —
   длинный ключ ломал бы запись в метку); отдельная SQL-таблица ключей (узлы
   появляются и мимо сверки — vault-ingest, запись агента, — таблица расходилась бы с
   графом). Выборка по метке, которой ещё нет, метку не создаёт. На существующих
   графах индекс строится при первом обращении сверки к существующей метке — записи
   (`upsert_entities`) или выборке по ключам (`existing_keys`/`close_entities`) —
   однократно, под транзакцией сверки.
   - **Кэш на процесс.** `CREATE INDEX IF NOT EXISTS` даже при существующем индексе
     берёт ShareLock таблицы метки до конца транзакции и сериализует параллельные
     сверки по одной метке, а выполнялся он на каждой выборке. Теперь «индексы метки
     есть» кэшируется на процесс (БД, граф, метка): повторные вызовы в БД не ходят.
     В кэш попадают только закоммиченные индексы — есть в каталоге и не держат
     блокировку нашего backend'а (`CREATE INDEX` держит AccessExclusiveLock на новом
     индексе до конца транзакции), так что откат транзакции, создавшей индекс, кэш
     не портит. `GraphStore.reset` сбрасывает кэш своего графа; граф, удалённый
     другим процессом, требует перезапуска сервиса (индексы иначе не удаляются).
   - **Имена индексов.** Метка до 48 символов — прежние имена
     `<метка>_pm_props_gin`/`<метка>_pm_nk_hash` (совпадают с уже созданными).
     Длиннее — первые 38 символов и 10 hex sha1 полного имени метки: раньше имя
     резалось до `label[:48]`, и вторая метка с общим префиксом молча оставалась без
     индекса (`IF NOT EXISTS` находил индекс первой).
3. **Повтор отложенных связей.** Отложенные связи других источников перепроверяются
   по **всем** сущностям снимка — открытым и подтверждённым (без изменений), а не
   только впервые открытым этим источником. Иначе связь, чей конец уже держит
   открытым этот источник, но узла не было в момент её сверки (узел удалён через API
   и вернулся записью агента или новой версией), ждала следующего снимка своего
   источника. Цена — один запрос к журналу по частичным индексам `ref_from/ref_to`
   на сверку.
   Сколько отложенных связей (своих и других источников) перепланировано сверкой,
   ответ показывает счётчиком `relations.retried` (аддитивно); сколько из них стало
   рёбрами — `relations.resolved`.

## Амендмент: канал resolve компилятора контекста (2026-09-23)

TAI-ADR-0042 п.4: «сначала детерминированное разрешение». Факт на staging: граф пакета
software-delivery в namespace workspace загружен сверкой (сотни эндпоинтов, методов
клиента, ADR, событий, таблиц), ядро спрашивает `POST /api/memory/context` с описанием
задачи в `query`, но `related_entities` всегда пусто: graph expansion стартует только
от якорей ядра (`task:`/`workspace:` — не ключи сущностей) и от векторных хитов (у узлов
сверки нет чанков), а точного поиска по узлам графа в `build_context` нет. Типизированный
обход (`/context/typed`) разрешает якоря, но ядро его не зовёт и якорей-ключей не знает.

**Решение.** У `build_context` новый канал-кандидат `resolve` (`context/resolve.py`),
во всех стратегиях, кроме `semantic`. LLM и вектор в нём не участвуют.

1. **Кандидаты** — якоря запроса (`anchors`, `subject`; `{type, id}` даёт `id` с
   подсказкой вида) и идентификаторы из `query`: `idPatterns` видов пакетов каждого
   namespace запроса (домен приходит данными пакета) и общий извлекатель
   `core.identifiers`. Порядок — якоря, затем по первому появлению в тексте; кандидат,
   целиком входящий в другой (`ADR-0062` в `CP-ADR-0062`, путь в `POST <путь>`),
   отбрасывается — разрешается более точная форма. Не больше **40** кандидатов.
2. **Порядок разрешения** кандидата — до первого успешного шага: (а) точный ключ;
   (б) псевдоним (`aliases` версии — формы ключа по шаблонам `aliases` вида и явные
   псевдонимы снимка: так `ADR-0035` находит `*-0035` всех рядов, `CP-ADR-0061` —
   `CP-0061`, `MEM-ADR-020` — `MEM-020`, путь с исходными именами параметров —
   эндпоинты всех методов); (в) `normalized` — ключ/псевдоним формы, где параметры
   `{name}` приведены к `{}` (`POST /goals/{goal_id}` → `POST /goals/{}`); (г)
   `suffix` — ключ оканчивается кандидатом (или нормализованной формой) по границе
   разделителя ` `/`.`/`:` (путь без метода — все методы, `get_claimability` и
   `ControlPlaneClient.get_claimability` — `<repo>:<module>.<Class>.<method>`, имя
   таблицы — `<repo>:<table>`); кандидат короче 4 символов суффиксом не ищется.
   Правила ADR-ссылок — данные пакета (`aliases` вида `adr`), в коде домена нет;
   обобщённые правила кода — только `{name}` → `{}` и суффикс по разделителю.
   Регистр и ведущие нули не нормализуются (`ADR-62`, `MEM-0020`, `cp-adr-0062` не
   разрешаются, пока соответствующей формы нет в `aliases` пакета/снимка): нормализация
   номеров держится на `aliases` пакета, код её не угадывает.
3. **Индекс — журнал версий сверки** (`<snapshots_table>_items`), актуальные строки
   (`valid_to IS NULL`; при `as_of` — валидные на момент): ключ — существующий
   `key_idx`; псевдоним — новый GIN `aliases_idx` по `payload->'aliases'`; суффикс —
   новый B-tree `rkey_idx` по `(namespace, reverse(item_key) COLLATE "C")`, диапазон по
   перевёрнутому ключу на каждый суффикс (`LATERAL`, не больше 10 на кандидата).
   Индексы частичные (`item_type = 'entity'`), создаются `ensure_schema` журнала
   (lifespan, `cb init-db`, сверка) — аддитивно. Не больше трёх запросов на компиляцию;
   видимость по principal (MEM-ADR-019/021) — в SQL по `payload->'scopes'` (тот же
   предикат, что у наблюдений), запрошенные `scopes` — пересечение или без scopes, как
   у graph-канала. Разрешённая версия должна существовать узлом графа (выборка по
   hash-индексу ключа метки, `existing_keys`): узел, удалённый через API, не всплывает.
   Не больше **20** разрешённых сущностей; одна сущность — один раз. Лимит раздаётся в
   два прохода: сначала точные совпадения (шаги а–в) всех кандидатов, затем суффиксные
   на остаток в порядке текста — неоднозначные имена методов в начале запроса не
   вытесняют точный ключ (правка по ревью TASK-000330).
   Видимость проверяется по `payload.scopes` **версии в журнале** (scopes, с которыми
   источник пришёл в сверку), а не по свойствам узла графа; если один ключ пришёл из
   нескольких источников, невидимые версии отсекаются в SQL, и заголовок, атрибуты и
   цитата сущности берутся из последней видимой версии.
4. **Выдача.** Разрешённая сущность — кандидат `entity` (`id = node:<ключ>`, как у
   graph-канала) с `signals.evidence = "resolved"`, `signals.resolve = {input, method,
   exact}`, цитатой `source_path` версии (`repo@sha:path:line` из provenance снимка;
   без неё — `snapshot:<source>/<snapshotId>`) и `provenance.snapshot`. Разрешённые —
   отдельные seeds graph expansion (своим вызовом и лимитом `context_max_nodes`, глубина
   `context_max_depth` ≤ 2): соседи якорей ядра не вытесняют окрестность контрактов;
   соседи, закрытые на `as_of`, отсюда не берутся; scope-фильтр и `is_visible` — прежние.
   Документ, найденный только вектором, помечается `evidence = "inferred"` без изменения
   score.
5. **Ранжирование.** Вес канала в RRF — 1.0; бонус `+0.040` за точное разрешение
   (ключ, псевдоним, нормализованная форма) и `+0.015` за суффикс. Точное разрешение
   выше любого наблюдения: максимум наблюдения (lexical + recent + идентификатор +
   scope + свежесть) ≈ 0.0452, минимум точно разрешённой (ранг 19, без прочих бонусов) —
   1/80 + 0.040 = 0.0525. Бюджет
   жадный по score — контракты не вытесняются свежими наблюдениями.
6. **Объяснимость.** `stats.channels.resolve`, `stats.resolved[]` (`{namespace, kind,
   key, method}`); трейс: `request.resolve_candidates` и `decisions.resolve` — по
   кандидату, чем и во что он разрешён, и лимиты.

Контракт `/api/memory/context` расширен аддитивно (новые `signals`, поля `stats`);
ядро и клиент не меняются. Нет совпадений — выдача прежняя (тест сравнивает с
отключённым каналом).

**Последствия.** Канал видит только сущности, пришедшие сверкой: узлы vault-ingest и
записи агента (без журнала) по-прежнему находятся якорями/вектором. Суффиксный поиск
шире точного — поэтому слабее бонус и лимит 10 на кандидата. Рёбра graph expansion
(`expand_neighbors`) по-прежнему без фильтра валидности (см. «Consequences»).
Лимиты — константы `context/resolve.py`; вынос в `CB_*` — при первой потребности.

**Отвергнуто.** Поиск по графу AGE (`MATCH (n) WHERE n.natural_key IN …` без метки и
`$alias IN n.props.aliases` — полный скан всех меток; по меткам — запрос на каждый вид);
триграммный/LIKE-поиск по ключу (не детерминирован по границам, `LIKE` с параметром
планируется непредсказуемо — диапазон по перевёрнутому ключу всегда индексный);
разрешение LLM или вектором (TAI-ADR-0042 п.4: сначала детерминированное; семантический
добор есть только в `/context/typed` при явном `allow_semantic`).

## Амендмент: typed-контекст разрешает якоря через resolve_candidates (2026-09-25)

TAI-ADR-0042 п.4; найдено на ревью TASK-000281 (control-plane). `/context/typed`
разрешал якоря только точным ключом, псевдонимом и `idPatterns`; канал resolve
(амендмент выше) умел ещё нормализацию плейсхолдеров и суффикс. Якорь в неточной форме
(эндпоинт без метода, `{id}` вместо `{goal_id}`, файл без префикса репозитория, имя
таблицы) уходил в `unresolved`, и потребитель (Control Plane, `context_schema`)
копировал нормализацию к себе.

**Решение.**

1. **Одна реализация.** Якорь typed разрешается тем же `resolve_candidates`
   (`context/resolve.py`), что и канал resolve: кандидат — значение якоря с подсказкой
   вида, по каждому namespace запроса. Порядок шагов — до первого успешного:
   `natural_key` → `alias` → `id_pattern` → `normalized` → `suffix` → `semantic`
   (последний — только при `allow_semantic`). Точный ключ остаётся первым шагом —
   прежние запросы разрешаются как раньше.
2. **Журнал и граф.** Журнал сверки даёт шаги `alias`, `normalized`, `suffix`;
   графовые запросы шагов `natural_key`/`alias` сохраняются и добирают сущности без
   журнала (наблюдения, записи API, ключи `<kind>:<value>`). Журнал спрашивается,
   только если точный ключ не нашёлся графом (не больше трёх запросов к журналу на
   якорь и namespace). Сущность из журнала должна существовать узлом графа — узел,
   удалённый через API, якорем не становится (как в канале resolve). Лимиты
   `resolve_candidates` — прежние (суффиксом не больше 10 на якорь, минимум 4 символа);
   лимиты typed (20 якорей, 10 шагов, глубина 5, 200 на шаг) не меняются.
3. **Выдача (аддитивно).** У якоря — `matchedBy` (самый точный шаг, которым он
   разрешён); у каждой разрешённой сущности — прежние `method` и `evidence`
   (`normalized` — `asserted`: тот же ключ с другими именами параметров; `suffix` —
   `extracted`, как `id_pattern`). Если неточный шаг (`normalized`/`suffix`) дал больше
   одной сущности — `ambiguous: true` и `candidates` (`{namespace, kind, natural_key}`).
   Якорь разрешается во все кандидаты — это не выбор одного, а полный набор (путь без
   метода — все методы пути): обход «кто вызывает» получает вызывающих всех
   методов, а вызывающий видит неоднозначность и может сузить якорь. Точный псевдоним
   с несколькими сущностями (`ADR-0035` → все ряды) неоднозначностью не считается, как
   и раньше.
4. **Вид `table`** пакета software-delivery отдельного правила не требует: имя таблицы
   разрешается суффиксом `<repo>:<table>` ← `<table>` (обобщённое правило кода, не
   домен); якорь `{kind: "table", value: "runs"}` находит `control-plane:runs`, таблицы
   с тем же именем в разных репозиториях — `ambiguous`. Пакет в этом репозитории —
   только фикстура тестов (копия `software-delivery.yaml` суперпроекта); для точного
   разрешения и извлечения имён таблиц из текста канала resolve пакет суперпроекта может
   добавить `aliases: ["<table>"]` виду `table` — это правка данных пакета, код не
   меняется.

Имя поля `matchedBy` — по запросу потребителя (camelCase, как поля запроса); остальные
поля ответа typed — snake_case. `client/` не меняется: `TypedContextPack.anchors` —
словари, новые поля проходят без правки модели.

**Отвергнуто.** Вторая реализация нормализации/суффикса в typed по графу AGE — полный
скан меток (см. «Отвергнуто» канала resolve) и расхождение двух каналов; при
неоднозначности не разрешать якорь вовсе — задача с эндпоинтом без метода снова не
получала бы вызывающих; выбирать «лучший» кандидат — угадывание, которого TAI-ADR-0042
п.4 не допускает.

## Амендмент: пакетное разрешение якорей и обход без просмотра всего графа (2026-09-25)

Найдено при проверке пакета контекста coding-task v3 на staging (TASK-000281,
CP-ADR-0064; память после амендмента выше). `POST /api/memory/context/typed` с одним
якорем (эндпоинт, разрешение `normalized`) и одним шагом (`calls`, in, depth 1) — 1,57 с
на 2 vCPU; профиль coding-task (4 якоря, 3 шага) — около 8 с, в таймаут ядра (3 с) не
укладывался.

**Профилирование** (`benchmarks/typed_context.py`: снимки software-delivery пяти
синтетических репозиториев — 7950 сущностей, 12530 связей — и узлы другого namespace
в том же графе; время — p50 на машине разработчика, SQL — на запрос):

| профиль | узлов чужого ns | было | стало |
|---|---|---|---|
| 1 якорь + 1 шаг | 20 000 | 76 мс, 18 SQL | 13 мс, 17 SQL |
| 1 якорь + 1 шаг | 200 000 | 286 мс | 12 мс |
| coding-task (4 якоря, 3 шага) | 20 000 | 196 мс, 37 SQL | 21 мс, 24 SQL |
| coding-task | 200 000 | 696 мс | 20 мс |

По фазам до правки (200 000): разрешение якорей — 163/435 мс (7/19 SQL), шаги
обхода — 118/244 мс, загрузка версий журнала для видимости — 4/14 мс (2/7 SQL),
служебные запросы и трейс — < 1 мс. Время росло с **размером всего графа**, а не
namespace запроса: графовые запросы typed шли без метки — `MATCH (n) WHERE
n.natural_key IN $keys` (точный ключ, `idPatterns`, узлы найденных журналом
сущностей), `$alias IN n.props.aliases` и `MATCH (a)-[r:REL]->(b) WHERE a.natural_key
IN $keys` в шаге. AGE транслирует такой `MATCH` в просмотр всех таблиц меток вершин
(узлы всех namespaces, включая документы vault), hash-индекс ключа метки
(второй амендмент) не применяется ни к `IN $keys`, ни к неразмеченному узлу. Запросов
было по одному на пару якорь × namespace × шаг разрешения и на уровень × namespace ×
направление обхода, журнал — до трёх запросов на пару якорь × namespace (ревью 356
п.4), версии журнала — на каждую пачку узлов. После правки фазы (200 000): якоря —
8/11 мс, обход — 1/2 мс, видимость — 3/6 мс; время от размера чужих namespaces не
зависит.

**Решение.**

1. **Якоря — пачкой.** Все якоря во всех namespaces разрешаются одним заходом
   (`_Compiler.resolve_anchors`): (а) граф — один запрос точных ключей якорей (с
   `<kind>:<value>`) и идентификаторов из `idPatterns`; (б) только для пар якорь ×
   namespace без точного ключа — журнал через `match_candidates` (`context/resolve.py`,
   общая часть с каналом resolve): ключи и псевдонимы всех форм всех якорей — по
   запросу, суффиксы — одним, не больше трёх запросов на весь запрос; (в) граф — один
   запрос узлов найденных журналом сущностей и псевдонимов узлов без журнала; версии
   журнала для видимости — одной выборкой после (а) и после (в). Семантика прежняя:
   шаги до первого успешного — отдельно на каждую пару якорь × namespace, лимит
   суффикса — 10 на namespace (`entities_by_suffixes(per_namespace=True)`), точных
   совпадений журнала — 20 на пару. Итого разрешение — 2 запроса, если все якоря
   нашлись точным ключом, и не больше 7 при любом числе якорей и namespaces.
2. **Графовые запросы — по меткам.** `GraphStore.lookup_nodes` — одна cypher-выборка
   `UNION ALL` по меткам видов якоря (вид с псевдонимами пакета; без вида — все метки
   вершин графа, `graph_labels()`): ключ — `UNWIND` + равенство (hash-индекс ключа
   метки), псевдоним — вхождение `{props: {aliases: [v]}}` (GIN свойств метки). Метка,
   которой нет в графе, ничего не находит.
3. **Шаг обхода — по graphid.** Узлы якорей и достигнутые узлы приходят с `_gid`
   (graphid вершины). `GraphStore.typed_neighbors` на уровень BFS делает два запроса на
   весь фронт всех namespaces и направлений: рёбра — из таблицы метки связи по
   `start_id`/`end_id`, концы — по graphid из таблиц их меток (id метки — старшие 16 бит
   graphid), затем одна загрузка версий журнала. Фильтр валидности ребра на `as_of`,
   `evidence_lost`, namespace конца, порядок (namespace, направление, ключ откуда,
   ключ куда, id ребра) и предел `limit*5+50` рёбер на namespace и направление —
   прежние. Валидность (`valid_to IS NULL` либо интервал `as_of`, сравнение моментов
   побайтово), `evidence_lost` и namespace ребра (свойство `namespace` фактов сверки)
   проверяются **в SQL до лимита** — операторами agtype по `properties`: у хаба,
   накопившего за сверки закрытые версии рёбер с меньшими id, они не вытесняют
   действующие (ревью 367 п.1). Рёбра vault без свойства `namespace` соединяют узлы
   одного namespace по построению (`upsert_edge`), конец сверяется с namespace старта
   ещё раз по загруженному узлу. Действующих рёбер на уровень читается не больше
   20 000 (по возрастанию id; лимит общий на весь фронт уровня); если их больше — у
   шага в `stats.steps[]` `truncated: true`. У меток рёбер — B-tree по `start_id` и
   `end_id` (`ensure_label_index`, создаются вместе с GIN при записи фактов связи;
   на действующих графах — при следующей сверке с этой связью): выборка фронта —
   bitmap index scan, а не просмотр таблицы связи.
4. **Выдача (аддитивно, из ревью 356).** `truncated: true` у якоря — шагу, который его
   разрешил, подошло больше сущностей, чем отдано: суффиксу — больше 10 сущностей
   допустимого вида в namespace (отданы первые 10 по ключу), точному шагу журнала —
   больше 20 (`MAX_RESOLVED`). Виды кандидата уходят в запрос суффиксов фильтром до
   лимита (`entities_by_suffixes(kinds=…)`), счёт — по различным сущностям
   допустимого вида: сущности других видов с тем же суффиксом не дают ложного
   `truncated` и не занимают места нужных (ревью 367 п.3).
   `ambiguous`/`candidates` считаются только по неточным шагам (`normalized`/`suffix`):
   точный ключ в одном namespace и единственное совпадение суффиксом в другом — не
   неоднозначность. Канал resolve не меняется: его `truncated` — по-прежнему
   исчерпание `MAX_RESOLVED`.

5. **Фазовый тайминг всего запроса (ревью 367 п.2).** Бенчмарк меряет только
   компиляцию на прогретом соединении, а на staging тот же профиль занимал 1,57 с —
   время может уходить вне компиляции (подключение к БД на запрос, IAM, видимость,
   PII-барьер). Компиляция отдаёт фазы в `stats.phases_ms` (`connect`, `setup`,
   `anchors`, `traverse`, `versions` — загрузка версий журнала для видимости, внутри
   `anchors`/`traverse`, `assemble`, `trace`). При `CB_SERVER_TIMING=true` ASGI-middleware
   (`core/timing.py`, `server/app.py`) собирает фазы всего HTTP-запроса — `auth`,
   `visibility`, `typed` и `typed.*`, `protect`, `total` (до начала ответа, с
   сериализацией) — в заголовок `Server-Timing` и строку лога `platform_memory.timing`.
   По умолчанию выключено: длительности раскрывают устройство сервиса. Локально
   подключение (`connect`: libpq + `LOAD 'age'` + OID agtype) — 2–3 мс; пул соединений
   и кэш проверки токена — следующим шагом, если замер на staging покажет основное
   время вне компиляции.

Лимиты typed (20 якорей, 10 шагов, глубина 5, 200 на шаг) и остальной контракт ответа
(`matchedBy`, `resolved`, `unresolved`, `sections`, `facts`, `used`) не меняются;
ответы старой и новой реализации на наборе профилей бенчмарка (якоря без вида, `both`,
depth 3, `as_of`, два namespace, scopes) совпадают с точностью до порядка: прежде
порядок `resolved` якоря и `used.entities` при нескольких совпадениях зависел от
порядка просмотра таблиц AGE, теперь он детерминирован. Регрессия — число SQL на запрос и
отсутствие неразмеченных графовых запросов (`tests/integration/test_typed_performance.py`:
один якорь + шаг — не больше 17, coding-task — не больше 24, 20 якорей — столько же, сколько 4),
валидность рёбер до лимита — `tests/integration/test_typed_edges_validity.py` (хаб с
закрытыми рёбрами числом больше лимита чтения).
После вливания ядру можно вернуть `CP_CONTEXT_TIMEOUT_SECONDS` к умолчанию.

**Последствия.** Шаг обхода читает таблицы AGE (`<граф>."<СВЯЗЬ>"`, таблицы меток
вершин) прямым SQL, а не cypher: так не нужен неразмеченный узел на другом конце. Это
привязка к раскладке хранения AGE (таблица на метку, id метки в старших битах graphid,
свойства — agtype с операторами `->>`) — та же, на которую уже опираются индексы меток
(второй амендмент). Рёбра связи выбираются по индексам `start_id`/`end_id` метки
связи; у меток, куда пишет только vault-ingest (`upsert_edge` индексов не создаёт), —
просмотром таблицы одной связи: стоимость пропорциональна числу её рёбер, а не
размеру графа.
Якорь без `kind` по-прежнему просматривает все метки вершин (одним запросом) —
потребителю выгодно передавать вид. Целевые цифры staging (≤ 0,3 с и ≤ 1,5 с) на
машине разработчика перекрыты с запасом больше порядка; подтверждение на staging —
за владельцем.

**Отвергнуто.** Индексы по `id` вершин и `start_id`/`end_id` рёбер, чтобы шаг остался
одним cypher-запросом: неразмеченный конец ребра — это `Append` по всем меткам, и
метки без индекса (vault, наблюдения) всё равно просматривались бы (индексы концов
рёбер для прямого SQL шага — приняты, п.3). Проверка namespace конца соединением с
таблицей вершин в том же запросе (до лимита): конец неизвестной метки — `Append` по
всем меткам вершин на каждое ребро; namespace ребра-факта в его свойствах и
построение рёбер vault в одном namespace дают тот же результат без соединения. Метки концов из `fromKinds`/`toKinds` пакета — теряли бы
рёбра нестрогих namespaces и записей API между видами вне пакета. Кэш результатов —
не лечит холодный запрос и требует инвалидации по сверке.

## Consequences

- Движок не содержит ни одного домена в коде: `default` — файл данных, домены
  потребителей — пакеты в БД. Существующие инсталляции без пакетов и строгого
  режима работают как раньше (прежние тесты зелёные без изменения проверок).
- Новые таблицы создаются lifespan'ом и `cb init-db` (аддитивно); тесты изолируют
  их суффиксом, как остальные.
- `POST /api/memory/context` (graph-канал `expand_neighbors`) **по-прежнему не
  фильтрует рёбра по валидности** — ТЗ P1a требовало валидность в новом обходе;
  перевод старого канала на тот же фильтр меняет выдачу существующих потребителей
  и оставлен отдельным решением.
- Известные пределы P1a: смена вида сущности между снимками создаёт
  второй узел (MERGE в AGE идёт по метке) — источник должен держать вид стабильным;
  vault-ingest использует каталог `default`, а не пакеты из БД; MCP-сервер и CLI
  новых операций пока не отдают.
- Регулярные выражения пакетов исполняются движком: регистрация ограничена
  service scope, длина шаблона ≤ 300, не больше 10 шаблонов на вид.

## Alternatives

- **Онтология кодом с плагинами** (Python entry points) — противоречит
  product-neutral и требует деплоя движка под каждый домен.
- **Полная JSON Schema через `jsonschema`** — новая runtime-зависимость (сейчас
  транзитивна только через extra `mcp`); подмножество покрывает ключи и атрибуты
  сущностей; при необходимости — отдельным решением с обновлением `THIRD_PARTY.md`.
- **Диф снимков по графу без журнала** — нельзя отличить «пропало» от «записано
  другим источником» и восстановить атрибуты на `as_of`; реляционный журнал дешевле
  и даёт идемпотентность по `snapshot_id` одной строкой.
- **Расширить `/api/memory/context` полем `traverse`** — ответ другой формы на том
  же маршруте ломал бы клиентов, ожидающих ContextPack; отдельный маршрут аддитивен.
