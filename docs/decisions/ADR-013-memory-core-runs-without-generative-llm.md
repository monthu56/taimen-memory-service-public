# ADR-013: Ядро памяти работает без генеративной LLM; генерация — отдельный уровень

## Status

Accepted (2026-09-12; реализовано — `CB_QUERY_SYNTHESIZE_DEFAULT=false`, Context
Compiler без LLM (ADR-016), провайдеры fake/echo в тестах). Предложено 2026-07-27 по
решению владельца: «Для работы непосредственно именно памяти большая LLM не нужна.
Нужно ограничить эти контуры. LLM — это уже другой уровень и другие деньги».

## Context

Требование закрытого контура без интернета ([ADR-012](ADR-012-new-proprietary-code-compiled-by-default.md))
поставило вопрос, что именно должно работать внутри контура заказчика. Сегодня сервис ходит
во внешний OpenAI-совместимый шлюз за тремя разными вещами, и их цена несопоставима:

| Функция | Замер | Класс модели | Железо |
|---|---|---|---|
| Эмбеддинг запроса | 250–320 мс | небольшая энкодер-модель | CPU |
| Переранжирование кандидатов | 1785–1870 мс | кросс-энкодер **или** LLM-as-judge | CPU / GPU |
| Синтез связного ответа | 4407 мс | генеративная LLM | GPU, деньги |

Смешивать их в одном требовании — ошибка: первые две дёшевы и локализуемы, третья
принципиально другого порядка по стоимости.

**Ключевая находка: ядро уже не зависит от генерации.** Генеративная LLM вызывается ровно
в четырёх местах, и каждое выключено по умолчанию:

- `ingest/entities.py:89` — извлечение сущностей, `CB_EXTRACT_ENTITIES=false`;
- `retrieval/query.py:283` — синтез ответа, `CB_QUERY_SYNTHESIZE_DEFAULT=false`;
- `retrieval/rerank.py` — LLM-реранк, `CB_RERANK_ENABLED=false`;
- `graph/communities.py:109` — ярлыки сообществ, только CLI `cb`, вне пути запроса.

Включена генерация только на публичной витрине (`CB_DEMO_RERANK=true`). То есть настоящее
положение дел уже соответствует принимаемому решению — ADR его формализует и защищает
от эрозии, а не вводит заново.

Это согласуется с продуктовым приоритетом №2 из `CLAUDE.md`: **цитаты-источники в каждом
ответе**. Обещание продукта — проверяемая ссылка на оригинал, а не сгенерированная проза.
Красивый текст — приятное дополнение, и он не должен становиться условием работоспособности.

## Decision

1. **Ядро памяти определяется как: эмбеддинги + гибридный поиск (вектор + FTS) + графовая
   окрестность + переранжирование.** Всё это обязано работать **без единого обращения
   к генеративной LLM**, локально, на CPU.
2. **Переранжирование переводится с LLM-as-judge на кросс-энкодер — но требует GPU.**
   Точка расширения уже существует: `CB_RERANK_PROVIDER` (сейчас `llm`), добавление второго
   провайдера — около 40 строк, fallback на RRF при недоступности уже реализован.

   **Исправление первоначальной формулировки (2026-07-27).** Здесь утверждалось, что
   кросс-энкодер работает на CPU. Это неверно и опровергнуто замерами: кросс-энкодер делает
   **один проход на каждую пару** (запрос, кандидат), а не один проход на запрос, как
   би-энкодер. При `rerank_pool=20` это 20 проходов; `bge-reranker-v2-m3` — XLM-RoBERTa-large
   на 568 млн параметров, и на CPU он получается **в 4–10 раз медленнее** нынешнего
   LLM-реранка, а не быстрее. Единственный CPU-жизнеспособный кандидат — малый мультиязычный
   MiniLM, но он на русском корпусе дал статистически незначимый прирост, то есть «CPU +
   кросс-энкодер» — быстро и, вероятно, бесполезно.

   На GPU картина обратная: те же 20 пар — десятки миллисекунд против 1785–1870 мс, то есть
   ускорение в 40–90 раз при лучшем качестве. Выигрыш даёт не «кросс-энкодер вместо LLM»,
   а **«кросс-энкодер на GPU вместо LLM по сети»**.

   Модель: `bge-reranker-v2-m3` (Apache-2.0) — единственный из проверенных на русском,
   пригодный к коммерческой поставке. `jina-reranker-v3` работает лучше, но под CC-BY-NC-4.0,
   то есть заказчику его отдавать нельзя.
3. **Эмбеддинги переводятся на локальную модель**, запускаемую в процессе или рядом,
   без внешней сети. Модель и рантайм выбираются отдельно; ограничение по железу — CPU.
4. **Генерация выносится в отдельный, опциональный уровень над контуром памяти.** Она:
   - не является условием работы ни одного маршрута `/api/brain/*`, кроме явно запрошенного
     синтеза;
   - остаётся за сменной абстракцией `LLM` (`retrieval/llm.py`) — провайдер выбирается
     конфигом, включая отсутствие провайдера;
   - тарифицируется и продаётся отдельно: другой класс железа, другие деньги.
5. **Инвариант, подлежащий проверке тестом:** при полностью отсутствующей конфигурации
   генеративной LLM сервис поднимается, отвечает на `/api/brain/query`, `/recall`, `/search`
   и **отдаёт цитаты-источники**. Отсутствие генерации деградирует ответ до контекста
   с цитатами, но не до ошибки. Сейчас это верно де-факто; после принятия ADR должно
   стать проверяемым.

## Consequences

- **Поставка в закрытый контур становится реалистичной.** Заказчику нужны две небольшие
  модели на CPU, а не GPU-инференс. Требование «любая ОС и архитектура» остаётся дорогим,
  но выполнимым: это вопрос сборки рантайма и весов, а не наличия ускорителя.
- **Выигрыш по задержкам есть, но он меньше первоначальной оценки.** Изначально здесь
  утверждалось «~2.1 с из 4–6 с»; это исправлено. Локальные эмбеддинги действительно убирают
  сетевой вызов, но из замеренных 250–320 мс заметная доля — **наш собственный дефект**,
  а не сеть: `retrieve()` строит эмбеддер на каждый вызов (`retrieval/query.py:175`),
  а конструктор `OpenAIEmbedder` создаёт новый клиент `OpenAI(...)` — то есть новый пул
  httpx и новое TLS-рукопожатие на каждый запрос. Переиспользование клиента даст часть
  выигрыша без всякой смены модели. Реранк же ускорится только при наличии GPU (см. п.2
  решения). Суверенность и скорость совпали по направлению, но не в заявленном масштабе.
- **Утечка ключей перестаёт быть системным риском в контуре заказчика.** Сегодня контур
  обязан хранить ключ внешнего шлюза; после перехода ядро ключей не требует вовсе.
  Актуально: один и тот же токен шлюза светился дважды — 2026-05-29 и 2026-07-27.
- **Данные перестают покидать контур.** Сегодня тексты заказчика уходят на внешний шлюз
  при каждом реранке и синтезе — прямое противоречие требованию «данные в РФ»
  и режиму ПДн ([ADR-002](ADR-002-pii-protection.md)). Это решение его снимает для ядра.
- **Качество ранжирования изменится**, и это надо мерить, а не предполагать. Требуется
  golden-набор запросов с эталонной выдачей до перехода: порядок цитат-источников —
  часть продукта, а не деталь реализации.
- **Витрина `/demo` — единственное место, где генерация включена**, и она останется
  подключённой к провайдеру: это маркетинговая поверхность на нашей инфраструктуре,
  требование закрытого контура на неё не распространяется.
- **Артефакт потяжелеет** на веса двух моделей. Это цена, которую надо назвать в оценке
  требования «один артефакт на всех заказчиков».

## Alternatives

- **Держать генерацию обязательной частью памяти.** Отвергнуто: делает поставку в закрытый
  контур невозможной без GPU, привязывает продукт к внешнему провайдеру и противоречит
  тому, что обещает контракт (цитаты, а не проза).
- **Локальная генеративная LLM внутри контура памяти.** Отвергнуто как часть ядра — по
  стоимости железа. Не отвергнуто как **опциональный уровень**: владелец обозначил
  готовность решать вопрос GPU отдельно, если он возникнет.
- **Оставить LLM-реранк, но через локальную модель.** Остаётся жизнеспособным вариантом
  вопреки первоначальной оценке в этом ADR: `llama.cpp`/`llama-server` отдаёт
  `/v1/chat/completions`, `/v1/embeddings` **и** `/v1/rerank` (флаги `--embedding
  --pooling rank --reranking`) одним OpenAI-совместимым бинарём. То есть один компонент
  закрывает все три внешние зависимости, а код не меняется вообще — только `base_url`.
- **Отказаться от переранжирования вовсе.** Отвергнуто: [ADR-005](ADR-005-rerank-candidate-set.md)
  показал, что оно определяет состав и порядок цитат — то есть напрямую влияет на главный
  продуктовый инвариант.

## Открытые пункты

- Выбор модели эмбеддингов и кросс-энкодера, рантайма и формата поставки весов —
  отдельное решение по результатам идущего исследования.
- ~~**Миграция размерности эмбеддингов**~~ — **снято владельцем 2026-07-27**: «меня не волнуют
  старые базы». Совместимость с существующими инсталляциями не требуется, переиндекс с нуля
  допустим. Это убирает главный технический риск перехода и открывает окно свободы: пока
  обратная совместимость данных не нужна, размерность, схему и **сам движок хранения** можно
  менять без цены миграции. Окно закроется с первой платящей SMB-инсталляцией.
- Судьба `CB_EXTRACT_ENTITIES` (извлечение сущностей через LLM при ingest): по этому ADR
  оно относится к уровню генерации, значит в закрытом контуре недоступно. Нужно решить,
  приемлема ли деградация качества графа без него.
